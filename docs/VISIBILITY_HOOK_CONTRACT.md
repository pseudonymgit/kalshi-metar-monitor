# VISIBILITY HOOK CONTRACT

## Purpose

This document defines the architectural contract for
execution-safe visibility hooks in Phase A visibility work.

This contract is normative.
Visibility integration MUST comply with all constraints below.

## Scope

This contract governs where visibility hooks may observe
execution truth and how hooks must execute without introducing
causal coupling or nondeterministic behavior.

Execution authority remains in execution-domain logic only.

## Allowed Hook Boundary Types

Visibility hooks are allowed only at the following boundary types:

1. `post-ingestion-decision`
2. `post-transition-evaluation`
3. `post-hydration-evaluation`
4. `scheduler-loop-completion`
5. `replay-completion`

Any hook insertion outside these approved boundaries is prohibited.

## Mandatory Hook Timing Rule

A visibility hook MUST execute only after all of the following
have completed for the relevant boundary:

1. decision finalization
2. state mutation completion
3. emission authority completion

Hooks are post-fact observers only.
Hooks MUST NOT run during in-flight decision computation.

## Forbidden Hook Locations

Hooks are explicitly forbidden inside:

- transition decision branching
- ingestion acceptance guards
- scheduler cadence control
- alert eligibility logic
- replay ordering logic

No visibility callback may be invoked from any code path that can
alter branch selection, acceptance/rejection, loop timing,
alert eligibility, or replay sequencing.

## Visibility Isolation Model

Required one-way dataflow:

- `execution -> visibility`

Forbidden reverse dataflow:

- `visibility -> execution`

Visibility hooks may consume immutable snapshots of execution outcomes.
Visibility hooks MUST NOT mutate execution state, influence control flow,
or provide feedback signals consumed by execution decisions.

## Hook Failure Semantics

Visibility hook failure MUST:

- never raise into execution caller
- never retry synchronously
- never delay loop completion
- degrade silently to no-op

Execution completion semantics take precedence over visibility capture.
If visibility fails, execution proceeds unchanged.

## Determinism Safeguards

Visibility hooks MUST NOT introduce:

- wall-clock ordering authority
- randomness
- async ordering dependency
- blocking IO
- retry timing variance

Hook processing must remain deterministic relative to the
already-finalized execution outcome and must not become a new source of
ordering or timing authority.

## Standard Hook Interface Contract

All boundaries must emit a canonical envelope named
`visibility_event_envelope`.

Required envelope contents:

1. deterministic identity inputs
   - station identifier
   - day/session key
   - deterministic event sequence/ordinal inputs available at boundary
2. decision outcome snapshot
   - finalized decision classification/result
   - finalized transition/hydration/ingestion/replay outcome fields
   - finalized emission/skip outcome markers
3. execution context markers
   - boundary type (`post-ingestion-decision`, `post-transition-evaluation`,
     `post-hydration-evaluation`, `scheduler-loop-completion`, `replay-completion`)
   - execution mode marker (live or replay)
   - loop/run correlation marker generated by execution domain

Envelope values MUST be derived from finalized execution state and
must not require additional decision logic inside visibility handlers.

### Envelope Materialization Rule

1. `visibility_event_envelope` MUST be fully constructed
   synchronously at the approved hook boundary.
2. Envelope fields MUST be copied from finalized execution state
   at boundary time.
3. Visibility handlers MUST operate only on the immutable
   envelope payload.
4. Visibility processing MAY be asynchronous ONLY AFTER
   envelope materialization.
5. Visibility handlers MUST NOT read live execution state,
   shared mutable objects, or recompute decision data.

Envelope materialization time defines the deterministic
observation moment.

## Structural Enforcement Requirement

Any new visibility capture point MUST map to one approved boundary type
and use `visibility_event_envelope` as defined above.

If a proposed hook cannot be expressed through an approved boundary,
it is out of contract and MUST NOT be added.

## Success Condition

This contract is satisfied only when engineers can add visibility
capture exclusively through approved post-execution boundaries,
with causal violations made structurally impossible by design.
