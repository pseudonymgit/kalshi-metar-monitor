  **2026-09-07T21:05Z**.

**M4 is not met: zero evaluated days. Cause is a chain, not one fault.**

### 1.2 The live daemon predates M1 (so it does not run the new writer)
- `ps`: `intraday_daemon.py` PID 831493 **started 06:19 UTC** (2026-10-03), from the
  pre-M1 checkout.
- M1 (`08c5a3fcc`) and M2 (`464690b7e`) were committed at **16:14 / 16:19 UTC**.
- The running process loaded `intraday_runner` **without** the `results_by_day` accumulate +
  `persist_results_to_db` block. **A restart is required for M1 to even execute.**

### 1.3 But even a fresh run of the M1 code writes nothing — the gate is closed upstream
Running `intraday_runner.py --no-lock --dry-run` (fresh interpreter, post-M1 code) produced the
`G.8 persistence` line **never** — not even the `0 result rows` branch. Trace:
1. Hourly signals evaluate to **zero fired signals**
   (`HourlySignalEvaluator.evaluate_hour_with_pool_names` → `pool_n=1`, `fired=0` for every station).
2. Fusion still returns a dict of 20 entries, but every value is `None`
   (`fused_results[st] = None` when `fired` is empty) → `Fusion complete: 20 stations` yet
   `fused_stations: 0` in the cycle summary.
3. The additive loop (`for st in stations: if st not in fused_results or fused_results[st] is None:
   continue`) therefore iterates **zero** times → `results_by_day` stays empty.
4. No `results_by_day` → the `if results_by_day:` persist block is skipped → no log, no rows.
5. Calibration likewise: `Calibration complete: 0 stations calibrated`.

So M1 is **correct but starved**: nothing reaches it. The writer is not broken; its input is empty.

### 1.4 Compounding defect: `AdditiveContext` cannot reach its sources (schema drift)
Direct probe: `AdditiveContext(station, today).__init__` logs
`METAR DB not available for <station>` for every station despite the DBs existing. Cause —
`core/additive/context.py::_load_metar` (and `_load_cloud`) query **columns/tables that do not
exist**, the `sqlite3.OperationalError` is swallowed by a broad `except`, and only a debug line is
emitted:

| Query in `context.py` | Reality | Effect |
|---|---|---|
| `metar_observations(valid, tmpf, …)` | column is `timestamp_utc`, `temp_f` | METAR today + trailing highs empty |
| `weatherapi_archive_hourly(hour, cloud)` | table is `hourly`, cols `hour,cloud` | cloud bucket empty |

Result: even if the additive loop ran, every `AdditiveContext` would be built from empty windows —
a silent zero, not a crash.

### 1.5 What M4 needs (not done — needs a call; see §3.2)
To emit a nonzero evaluated-day receipt: (a) restart the daemon on M1 code, **(b)** fix the hourly
signals/fusion so at least one station fires (or bypass fusion for additive evaluation and evaluate

drift, **(d)** fix the enrichment wiring (M7, §3). Then re-run one cycle and query
`additive_signal_results`.

**all-zero artifact**: every one of its 120 `(station, market-type, direction)` cells carried

  (120/120 zero cells, 20/20 zero stations).
- Regenerated by M8 (§4): 80/80 cells nonzero, sha256
  `0317d23ac23dc1b950ca5d6951d0c56d6828fd21ce6bb89477e767c2268fb759`.

Note: the *runtime* `0 stations calibrated` also depends on the fusion gate (§1.3) — with
`fused_results` all `None` the calibration loop has no stations to iterate regardless of curves.
Both must be true to see calibrated output: fresh curves **and** a fired fusion result.

## 3. M7 — ASOS/NWP enrichment reaching the daemon → **dead on the live path**

Verified by code + runtime, not by DB mtime.

### 3.1 The daemon attempts enrichment; the queries cannot succeed
`intraday_runner.py` constructs `HourlyPipeline(metar_db=…, asos_db=data/iem_asos_1min.db,
nwp_db=data/nwp_forecasts.db)` (non-empty), so `_enrich_from_asos` / `_enrich_from_nwp` **do run**.
Both fail on schema drift (logged at DEBUG, swallowed):
- `_enrich_from_asos` issues `SELECT … FROM t<station> WHERE valid LIKE ?`. The ASOS 1-min DB has a
  **single** table `observations` (cols `station, valid, tmpf, drct, sknt, …`) — there is **no
  per-station `t<station>` table** → `OperationalError` → skipped for every station.
- `_enrich_from_nwp` issues `SELECT … FROM nwp_hourly_forecasts …`. `nwp_forecasts.db` has table
  `nwp_forecasts` (cols incl. `station, target_date, model, variable, value`), **not**
  `nwp_hourly_forecasts` → `OperationalError` → skipped.

### 3.2 The signal evaluator bypasses enrichment entirely
`core/intraday/signal_evaluator.py` constructs `HourlyPipeline(metar_db=…, asos_db="", nwp_db="")`
in **both** call sites, so the `if not self.asos_db: return vectors` / `if not self.nwp_db: …`
guards short-circuit and **enrichment never runs** on the path that feeds signals — regardless of
the schema bugs above.

### 3.3 Conclusion
Live enrichment is **not** reaching the daemon: (1) the evaluator passes empty paths (skipped), and
(2) the runner's non-empty paths hit missing tables (swallowed). Signals are therefore built from
METAR-hourly only. Any future "enrichment is live" claim must be shown in a live evaluation
payload, not a fresh DB mtime.
